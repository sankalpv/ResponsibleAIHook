How we added the skill-load guard

The task was to run checks on every skill an agent loads, using agent-hooks' existing hook contract and without changing the spec. This page explains what we built, why it's shaped this way, and how we tested it.

In one paragraph: agent-hooks has 8 fixed checkpoints, and a host may not invent a ninth. So we didn't add a "skill load" checkpoint. Instead, the host loads every skill through one function, load_skill, which it reports as a tool call. That puts every skill load between two checkpoints that already exist: pre_tool_call (before the skill is read) and post_tool_call (after it's read, before the agent sees it). A new binding kind, com.example.skill-guard, sits at those two checkpoints and returns allow or deny.
  • The spec, the Rust core and the SDK APIs are unchanged.
  • It works on the released spec version 0.1.
  • We added three things: a docs page, one nav line, and a test file that runs the docs page's code.
  • A subagent code review and an end-to-end run then found 12 issues, several of which let a skill through. Section 7 lists them and how each was fixed.

1. The problem and the constraint

A skill is a packaged set of instructions (often a SKILL.md file) that an agent pulls into its context when it needs it. That makes it a way in for untrusted instructions. We want a gate that can block a skill based on which skill it is, where it came from, and what it contains.

Rejected Add a new skill_load checkpoint

The spec says (§3): "The set is closed; a host MUST NOT emit an AgentContext whose interception_point is not one of these values." A ninth checkpoint would mean changing:

  • the spec;
  • the schemas;
  • all five SDKs;
  • the conformance vectors;
  • the declaration format.

That is a large change.

Chosen Treat a skill load as a tool call

docs/INTEROP.md already uses this approach for MCP resource reads: things that aren't tool calls get covered by presenting them as tools. A tool call gets a before checkpoint and an after checkpoint, which are exactly the two gates we need. Nothing in the contract changes.

2. Walk through a skill load

Pick a scenario to see which steps run, where it stops, and why. The two outlined steps are the guard's two gates.

  1. 1
    Agent asks for a skillThe model, a user command, or the host itself wants e.g. pdf-tools.
  2. 2
    load_skill emits pre_tool_callTool name load_skill; args {name, source, version}, which are covered by the fingerprint.
  3. 3
    Guard, gate 1: which skill and where fromValid name → blocklist → trusted source → reviewed (allowlist).
  4. 4
    Approver (only for "unreviewed")A deny that a human approver can lift. With no approver registered, it stays a deny.
  5. 5
    Host reads the skillOnly after gate 1 allows. Any read error still emits step 6, as an error result.
  6. 6
    load_skill emits post_tool_callThe skill text is the result value, which is covered by the fingerprint.
  7. 7
    Guard, gate 2: what the skill containsRe-check name and source → is text → size limit → pinned SHA-256 → forbidden patterns.
  8. 8
    Skill enters the agent's contextThis is the only way in. A deny at step 7 means the host throws the text away.

3. The pieces we wrote

Everything lives in one new docs page, docs-site/docs/examples/skill-guard.md. It follows the same pattern as every other control in the repo: binding → kind resolver → interceptor → verdict.

3a. The binding (in the host's declaration file)

A binding says what to call (the kind), where (at), and with what settings (config). The kind is just a name; the host's own code decides what it means.

{
  "id": "skill-guard",
  "kind": "com.example.skill-guard",
  "at": ["pre_tool_call", "post_tool_call"],
  "timeout_ms": 2000,
  "config": {
    "trusted_sources": ["internal-registry"],
    "allow": { "pdf-tools": "sha256:c01c…a078", "sql-helper": null },
    "block": ["shell-anything"],
    "max_bytes": 262144,
    "forbidden_patterns": ["curl | sh", "ignore previous instructions"]
  }
}

The allow map pins each reviewed skill to the SHA-256 of its content. null means "any content that passes the other checks". The page also binds an explicit allow-all at the other checkpoints (including the two model ones, since an agent that loads skills calls a model), because in enforce mode a checkpoint with nothing bound denies everything (host_error:no_interceptor).

3b. The kind resolver: runs once, when the file loads

The host registers resolve_skill_guard under the kind name. When the declaration loads, the SDK calls it with the binding's config. It checks every key and refuses anything it doesn't understand. A refusal rejects the whole file (declaration_error:binding_rejected) before any agent runs, and its error message names keys, never values, because config can contain secrets. It also refuses any binding that is not on exactly both tool checkpoints: bound at only one, half the guard would silently do nothing.

registry = (
    HostRegistry(HostSurface.from_capabilities(["model_calls", "tool_calls", "host_declaration"]))
    .kind("com.example.skill-guard", resolve_skill_guard)
    .kind("com.example.allow-all", lambda config, binding: AllowAll())
    .approval_resolver("skill-review", SkillReviewQueue())
)
emitter = InterceptionEmitter.from_declaration_path("agent-hooks.declaration.json", registry)

3c. The interceptor: SkillGuard.intercept

It is called at every pre_tool_call and post_tool_call. It ignores (allows) every tool that isn't load_skill, so normal tool calls are unaffected. The checks run in a worker thread (asyncio.to_thread). The SDK's timeout can only interrupt an interceptor at an await, so a body that never awaited would run to the end however long it took.

async def intercept(self, ctx):
    return await asyncio.to_thread(self._check, ctx)    # so the timeout can fire

def _check(self, ctx):
    call = ctx.get("tool_call") or {}
    if call.get("name") != LOADER_TOOL:
        return Verdict.allow()                          # not a skill load
    args = call["args"]
    denied = self._screen(args)         # name slug, blocklist, trusted source: BOTH points
    if denied is not None:
        return denied
    if ctx["interception_point"] == "pre_tool_call":
        # not on the allowlist -> a deny an approver may lift; else allow
        return Verdict.escalate(...) if args["name"] not in self._allow else Verdict.allow()
    return self._after_load(args, ctx["tool_result"])   # gate 2: content

3d. The host gateway: load_skill

This is the single route every skill takes into the agent. It always emits both checkpoints, even when the read fails, because the spec requires each pre_tool_call to have its matching post_tool_call (§3.1).

async def load_skill(emitter, builder, read_skill, *, call_id, name, source, version):
    args = {"name": name, "source": source, "version": version}
    pre = await emitter.emit(builder.pre_tool_call(call_id=call_id, name=LOADER_TOOL, args=args))
    args = pre.target                                # args as the checks allowed them
    try:
        content = await asyncio.to_thread(read_skill, args)
        if not isinstance(content, str):
            raise TypeError("skill content must be text")
        failed = False
    except Exception as e:                           # any failed read is a tool error
        content, failed = f"skill could not be read: {type(e).__name__}", True
    post = await emitter.emit(builder.post_tool_call(
        call_id=call_id, name=LOADER_TOOL, args=args, value=content, is_error=failed))
    if failed:
        raise LookupError(f"skill {args['name']!r} could not be read")
    return post.target                               # content as the checks allowed it

On a deny, emitter.emit raises InterceptionBlocked. A failed read raises LookupError. The agent loop catches both and tells the model the skill wasn't loaded and why.

4. What the guard decides

CheckpointIf…Verdict
eitherthe tool isn't load_skillallow
eitherthe name isn't a lowercase slug ([a-z0-9][a-z0-9._-]{0,63})deny skill_guard:invalid_name
eitherthe name is on the blocklistdeny skill_guard:blocked
eitherthe source isn't trusteddeny skill_guard:untrusted_source
pre_tool_callthe skill isn't on the allowlistliftable deny skill_guard:unreviewed
post_tool_callthe read itself failedallow (nothing was loaded)
post_tool_callthe content isn't textdeny skill_guard:malformed
post_tool_callit's bigger than max_bytesdeny skill_guard:too_large
post_tool_callits SHA-256 doesn't match the pindeny skill_guard:tampered
post_tool_callit contains a forbidden patterndeny skill_guard:content_blocked

The first four rows run at both checkpoints. At post_tool_call they re-check the arguments the loader actually used, so another control (or an approver) that rewrites the name or source can't swap in a blocked skill. Names are matched exactly and never normalised, so Shell-Anything can't slip past a blocklist entry on a case-insensitive store.

If the guard itself crashes, times out or returns garbage, the SDK turns that into a deny (host_error:interceptor_failed and similar). A broken guard never lets a skill through.

6. How it's tested

The test file sdk/python/tests/test_skill_guard.py doesn't keep its own copy of the guard. It pulls the Python block out of the docs page and runs that exact code, through a real emitter built from a real declaration. If someone edits the page and breaks it, the test fails.

7. What the review and the end-to-end run found

We gave a subagent only the changed files and the contract, and asked it to find faults. A second subagent ran the page's code as written in a fake agent session (21 records) with real skill files. The end-to-end run confirmed every row of the original verdict table, so most findings were gaps beyond it. We re-checked the surprising ones ourselves before changing anything.

#FindingFix
1bug A binding at only one tool point was accepted, silently disabling half the guard.Resolver requires exactly both points.
2bug A loader_tool config key (or a typo in it) turned the guard off.Key removed; the tool name is a constant.
3bug Only OSError was caught, so other read errors skipped the post checkpoint; bytes content crashed the emitter.Any exception, and non-text content, becomes a failed read with only the type name.
4bug The timeout never fired: the async guard never awaited, so it could not be interrupted.Checks run via asyncio.to_thread; a test proves the timeout.
5bug The post check ignored the name/source actually used, so another control's or an approver's rewrite could swap in a blocked skill.Name and source are re-checked at both points; approval-skips-later-controls documented with the resume knob.
6bug Shell-Anything got only a liftable deny, not blocked.Strict name grammar; anything else is a plain invalid_name deny, also in config.
7doc Claimed contexts over 5 MiB are denied by default. The SDK enforces no size bound (also seen in the end-to-end run).Claim replaced: host must bound the read; max_bytes capped at 1 MiB.
8doc Told readers to keep on_error: deny, a member declaration 1.0 refuses.Sentence removed.

One check from the original end-to-end script now "fails" on purpose: it asserted the false 5 MiB claim. What it observed (the guard runs and denies the oversized skill as too_large) is what the corrected page says. Still open: lifting the guard's deny skips later controls under the default profile, and the SDK cannot serialise bytes into a context. Both are documented, not changed here.

9. Cost

Let n be the size of the skill text. Gate 1 is a few set lookups (constant time). Gate 2 encodes the text once, hashes it when a digest is pinned, folds its case once, and scans it once per forbidden pattern, so it is linear in n for a short pattern list (O(n·p) for p patterns; a multi-pattern matcher such as Aho-Corasick brings it to one pass). The checks run in a worker thread, so the timeout works, but a timed-out check is abandoned rather than killed, which is why max_bytes is capped at 1 MiB. The SDK already pays O(n) per checkpoint to fingerprint and copy the context. Memory is O(n) for one skill at a time.

10. What the host still has to do

  • One door only. Every skill must come in through load_skill. The spec doesn't promise complete mediation, so a second route would bypass the guard.
  • Bound the read. The SDK does not enforce the recommended 5 MiB context bound, so have read_skill stop at max_bytes + 1 bytes.
  • Bind something at the other checkpoints, including the model ones, or enforce mode denies them all.
  • If other controls follow the guard, set composition.on_approval to resume; otherwise lifting the guard's deny skips them.
  • Load on first use. Hosts that preload skills still call load_skill for each one, after startup has been allowed.
  • Treat patterns as a tripwire and pin digests for skills that matter.
